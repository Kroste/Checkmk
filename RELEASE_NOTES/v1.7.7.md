Zwei Nachbesserungen am Viewer-Modus aus v1.7.6: ein Filter-Bug, der die
Profilvorgabe aushebelte, und eine neue Option für Ausgaben, die dauerhaft auf
einem Bildschirm laufen.

## Behoben — der Viewer zeigte den falschen Filter

Im Viewer-Modus konnte die **persönliche `filter.json`** des Rechners, auf dem
das Profil gebaut wurde, die Vorgabe aus `viewer.json` überstimmen. Sichtbar
wurde das als „da stehen fremde Favoriten im Dropdown" und „es werden nur die
Hosts eines ganz anderen Filters angezeigt".

Zwei Ursachen, beide behoben:

1. Ein **leeres `hostRegex`** ließ den Vorgabefilter komplett unter den Tisch
   fallen. Damit blieb der zuletzt aktive Filter aus `filter.json` stehen. Ein
   leeres `hostRegex` heißt jetzt korrekt „alle Hosts" — der Filter trägt dabei
   trotzdem den Namen aus `filterName`.
2. Der Viewer-Modus **las die persönliche `filter.json` überhaupt**. Er lässt sie
   jetzt komplett außen vor: weder gelesen noch geschrieben. Der Filterzustand
   kommt ausschließlich aus dem Profil.

Als Folge sind „Filter verwalten…" und die Favoriten-Menüpunkte im Viewer-Modus
weg — sie hätten dort keinen Speicherort mehr.

Welcher Filter tatsächlich gegriffen hat, steht jetzt beim Start im Log — die
häufigste Frage beim Ausrollen:

```
INFO|StatusViewModel|Viewer-Vorgabe aktiv: Filter 'Alles' (Regex=—, 0 Hosts explizit),
NurProbleme=true, NurOffen=false, AutoRefresh=true/60s.
```

## Neu — Fenster springt bei Problemen auf

Für Ausgaben, die dauerhaft auf einem Bildschirm laufen (Wachschutz, Leitstand),
reicht ein Toast oft nicht. `"popUpOnProblem": true` (Standard im Viewer-Modus)
holt das Cockpit bei einer **Verschlechterung** selbst nach vorn: maximiert, ganz
oben im Stapel, mit markierter Zeile für den betroffenen Service. Liegt die App
im Tray, wird sie dabei wieder eingeblendet.

| Ereignis | Fenster springt auf |
|---|---|
| OK → WARN/CRIT (neues Problem) | ja |
| WARN → CRIT (Verschlechterung) | ja |
| CRIT → OK (Recovery) | **nein** |
| Snooze aktiv (Tray-Menü) | **nein** |

Sind mehrere Dinge gleichzeitig kaputtgegangen, springt die Ansicht auf das
schwerwiegendste. Abschalten mit `"popUpOnProblem": false`; der Toast bleibt
davon unberührt.

> Windows gibt einer Hintergrund-Anwendung nicht immer den Tastaturfokus. Das
> Fenster wird zuverlässig sichtbar und nach ganz oben geholt; ob es zusätzlich
> den Fokus bekommt, entscheidet Windows.

Warum ein Toast oder Popup kam — oder eben nicht — steht jetzt bei jedem Refresh
auf Debug-Ebene im Log:

```
DEBUG|TrayController|Refresh-Diff: 3 Services (CRIT 1/WARN 0/UNK 0/OK 2),
Aenderungen=1 (1 neues Problem), ImTray=false, Snooze=aus, PopUp=true.
```
